# 多链 DEX 统一交易终端：一键交易技术方案调研报告

> **文档状态：** 前期技术调研稿 / 供团队评审\
> **版本：** v0.1\
> **调研基准日期：** 2026-10-15\
> **产品范围：** 优先 EVM 链；首期必须支持单链 Swap
> 与跨链兑换；目标用户为普通个人用户\
> **核心议题：** 跨链路由与执行供应商选型、钱包技术方案、Gas
> 支付方案、成本模型与 MVP 验证计划

------------------------------------------------------------------------

## 1. 执行摘要

### 1.1 产品目标

建设一个面向普通个人用户的多链、多 DEX 统一交易终端。用户不必理解底层
DEX、桥接协议、跨链消息和不同链的 Gas 机制，即可在统一界面中完成：

-   同一条 EVM 链上的代币兑换；
-   不同 EVM 链之间的跨链兑换；
-   查看预计到账、最低到账、交易费用、预估耗时和风险提示；
-   在交易过程中查看源链提交、跨链处理中、目标链执行和最终完成等状态；
-   在失败、延迟或部分完成时获得清晰解释与下一步指引。

### 1.2 建议的总体策略

**优先采购成熟的跨链聚合和执行能力，把产品差异化放在用户体验、交易状态管理、费用透明、风险控制和供应商抽象层上。**

建议采用以下基线：

1.  **跨链路由：** 第一阶段优先评估 LI.FI 作为主候选，同时用
    Bungee/Socket
    或直接跨链协议做报价与能力对照。候选不是最终排名，必须以目标链、目标资产、交易金额和实际报价测试决定。
2.  **钱包：** 以外部 EOA 钱包作为基线，另做一条智能账户 / EIP-7702
    增强体验 PoC。不要把 ERC-4337 作为跨链交易的必选条件。
3.  **Gas：** 首先实现用户自行支付源链 Gas
    的可运行路径；并行评估平台赞助 Gas
    和代币支付执行费。跨链协议是否覆盖目标链 Gas 必须逐条路由验证。
4.  **执行层：** 区分
    DEX/跨链聚合器、Relayer、Bundler、Paymaster。它们解决的问题不同，不能因为接入某个
    Relayer 就认为已经获得跨链路由能力。
5.  **MVP 范围：** 先支持 2--3 条 EVM
    链、有限的主流代币和经过验证的跨链路径；暂不自建桥接协议、通用路由引擎或托管用户私钥。
6.  **上线门槛：**
    必须验证正常成功、目标链延迟、目标链执行失败、部分完成、退款/恢复等路径。跨链交易不是单一原子交易，不能只测试"成功一次"。

### 1.3 当前需要团队确认的决策

  -----------------------------------------------------------------------------------------------
  决策项                  推荐基线                             仍需确认
  ----------------------- ------------------------------------ ----------------------------------
  首期链范围              2--3 条 EVM 链                       具体链及优先级

  首期资产范围            主流稳定币和高流动性资产             代币白名单与风险政策

  跨链路由                先接一个聚合器，保留替换能力         主供应商和备用策略

  钱包                    外部 EOA 优先                        是否首期提供内嵌钱包

  Gas                     用户自行支付为基线，赞助为可选增强   赞助预算与适用用户

  收费                    先建立全成本模型，再决定平台费       是否收交易服务费、费率与最低收费

  自动化交易              首期不支持无人值守策略               是否纳入后续路线图
  -----------------------------------------------------------------------------------------------

## 2. 产品范围与 MVP 边界

### 2.1 首期必须实现

-   多 EVM 链网络选择与钱包连接。
-   读取用户在源链的代币余额、原生 Gas 余额和授权状态。
-   单链 Swap 报价与交易构造。
-   跨链 Swap 报价与路由选择。
-   显示预计到账量、最低到账量、各项费用、预估时间及报价有效期。
-   对 ERC-20 代币进行授权检查；需要授权时明确提示并引导用户完成。
-   用户确认后签名并提交源链交易。
-   持续追踪跨链流程和目标链结果。
-   保存交易记录、供应商路由信息、状态变化、费用估算和最终结果。
-   对交易失败、延迟、部分完成和需要用户采取行动的情况提供清晰提示。
-   基础风险控制：滑点限制、代币白名单或风险提示、交易模拟（供应商/链支持时）、最小到账量和报价过期处理。

### 2.2 首期建议不实现

-   自建桥接协议、跨链消息协议或 Solver 网络。
-   自建完整 DEX 聚合路由引擎。
-   自动套利、无人值守交易、复杂条件单。
-   全面支持非 EVM 链。
-   默认托管用户私钥或代替用户控制资产。
-   在没有明确成本收益证据前，强制所有用户使用智能账户。
-   对所有交易无条件赞助 Gas。
-   将所有跨链交易承诺为"即时完成"或"目标链失败必定自动退款"。

### 2.3 "多链"与"跨链"需要分开定义

-   **多链交易终端：** 用户可以在多条链上分别执行单链 Swap。
-   **跨链兑换：**
    用户从源链资产出发，最终在目标链获得另一种资产；通常涉及桥接、跨链消息或意图执行。
-   **跨链 Gas 抽象：** 用户不必预先在目标链持有原生
    Gas，或可用指定代币支付执行成本。它是独立能力，不能从"支持跨链兑换"自动推导出来。

### 2.4 用户旅程

1.  连接钱包或创建钱包。
2.  选择源链、源资产、输入金额。
3.  选择目标链和目标资产。
4.  获取可执行报价，显示预计到账、最低到账、费用、时间和路径。
5.  检查余额、授权、Gas 与报价有效期。
6.  用户确认交易；如需要授权，先完成授权步骤。
7.  用户签名并提交源链交易。
8.  后端记录源链交易哈希，持续追踪跨链执行状态。
9.  成功后展示目标链交易和最终到账量；若延迟、部分完成或失败，显示明确状态与可执行的恢复指引。

**产品原则：**
不把"发出源链交易"当作"跨链交易完成"。只有确认目标链最终结果后，才向用户展示完成状态。

### 3.3 必须自有的控制面

即使使用第三方聚合器，也建议由产品自己掌握：

-   内部订单 ID 和用户可见交易状态。
-   报价快照与用户确认时的关键参数。
-   源链与目标链交易哈希。
-   供应商、路由、费用和执行结果记录。
-   订单幂等性与重复提交保护。
-   用户可见的异常解释与恢复入口。
-   供应商切换和停用规则。

不要让前端仅依赖某家供应商的临时任务 ID
作为唯一订单记录，也不要把供应商返回的 `completed`
状态未经核验就直接等同于链上最终到账。

## 4. 跨链聚合器与执行供应商选型

### 4.1 供应商分类

  -------------------------------------------------------------------------------------------------------------------
  类别                  解决的问题                           代表候选            不能替代的能力
  --------------------- ------------------------------------ ------------------- ------------------------------------
  DEX 聚合器            单链多个 DEX 的报价与交易路由        1inch、0x 等        不自动提供完整跨链执行

  跨链聚合器            组合 DEX、桥接和跨链执行路径         LI.FI、Bungee 等    不等于产品自己的订单状态和风控系统

  跨链协议/流动性网络   具体的资产转移、跨链消息或意图执行   Across 等           不一定覆盖所有资产与链

  Relayer               代为提交符合要求的交易               Gelato、1Shot 等    不负责自动发现最佳跨链路径

  Bundler / Paymaster   智能账户 UserOperation 打包和 Gas    Etherspot、Gelato   不等于跨链桥或 DEX 聚合器
                        赞助                                 等

### 4.2 候选供应商初步判断

#### LI.FI：首选 PoC 候选

适合用来验证一个接口是否能覆盖单链 Swap、跨链桥接与目标链兑换。其 API
可返回报价、预计到账、最低到账、费用项及可提交的交易请求；支持按源链、目标链、资产、金额和路由偏好请求报价。

需要重点验证：

-   目标链与目标资产是否覆盖 MVP 需求。
-   报价是否包含桥费、目标链 Gas、服务费及平台集成费。
-   某些路径是否要求用户在目标链再次签名。
-   报价延迟、路径稳定性、实际到账与预估差异。
-   API 限流、生产支持、商业条款和 SLA。
-   失败、部分完成、退款和状态查询流程。

官方文档： - API / SDK：https://li.fi/api-sdk -
技术文档：https://docs.li.fi/ - Quote
接口说明：https://docs.li.fi/li.fi-api/li.fi-api/requesting-a-quote -
费用结构说明：https://help.li.fi/hc/en-us/articles/13304987014299-Can-you-share-some-insight-into-the-fees-structure-of-using-LI.FI-for-a-DApp -
商业 API 条款：https://li.fi/legal/commercial-api-terms-of-use

**当前费用线索：** LI.FI 帮助中心公开说明，标准集成交易费曾以 25
bps（0.25%）作为默认值展示，并支持通过集成设置配置；大交易量或企业合作可能有折扣或其他商业模式。此值必须在注册合作门户、实际报价和合同条款中复核，不应直接当作所有路由的总费率。DEX
费、桥费、Gas 和其他路由费用仍需单独计算。

#### Bungee / Socket：交叉验证候选

适合作为跨链聚合报价和执行路径的对照对象。研究重点包括支持网络、报价接口、交易构造、状态追踪、费用透明度、API
限制和生产支持。

官方入口： - Bungee：https://www.bungee.exchange/ -
文档：https://docs.bungee.exchange/ - Socket：https://www.socket.tech/

当前阶段不预设其报价或成功率优于
LI.FI。应在相同的链、资产、金额和测试时间下做并行报价与小额实测。

#### Across：直接协议对照

可作为跨链流动性/执行路径候选，与聚合器生成的 Across
路由进行对照。重点评估其在目标链、资产、金额、速度、费用、风险和恢复能力方面的适用性。

官方入口：https://across.to/

直接接协议可能获得更清晰的特定路径控制，但会增加集成和维护成本，也不意味着所有交易都更便宜或更快。

## 5. 钱包方案调研矩阵

### 5.1 候选方案

  ------------------------------------------------------------------------------------------------------------------------
  维度           A. 外部 EOA 钱包 B. ERC-4337 智能账户   C. EIP-7702 增强 EOA         D. 内嵌钱包 / Passkey
  -------------- ---------------- ---------------------- ---------------------------- ------------------------------------
  用户接入       连接已有钱包     依赖支持的账户/钱包    依赖钱包对授权流程的支持     可接近 Web2 注册体验

  原生 Gas       通常由用户准备   可通过 Paymaster 赞助  满足授权与执行条件时可抽象   取决于底层账户和执行服务

  批量执行       通常需额外机制   账户可支持批量执行     可通过委托逻辑实现           取决于账户实现

  开发复杂度     低               中高                   中高                         中高

  钱包兼容性     相对广           需核对账户与工具支持   需核对钱包与授权支持         依赖钱包供应商与恢复方案

  密钥恢复       钱包自身负责     取决于账户恢复模块     仍需考虑 EOA 密钥和委托安全  需要审查恢复、设备迁移与供应商依赖

  适用定位       MVP 基线         高级交易体验           逐步增强既有钱包体验         降低新用户门槛
  ------------------------------------------------------------------------------------------------------------------------

### 5.2 推荐验证路线

**路线 A：外部 EOA 基线** - 连接钱包、余额检查、ERC-20 allowance
检查。 - 用户完成授权与源链交易签名。 - 跨链执行由聚合器/协议处理。 -
明确用户是否需要在目标链再次签名。 -
测量从连接钱包到完成交易的操作次数与失败点。

**路线 B：智能账户或 EIP-7702 增强** - 验证交易批处理和 Gas
赞助是否可用。 - 检查账户、链、钱包和供应商的兼容矩阵。 -
验证授权的有效范围、撤销机制、委托代码与目标合约安全。 -
统计新增费用、开发复杂度和用户体验收益。

### 5.3 钱包选型原则

1.  不要仅为了"跨链"就引入智能账户；跨链路由与钱包账户模型是两个不同层面。
2.  不要把 EIP-7702 理解为所有普通 EOA 交易都能无条件免
    Gas。必须满足具体授权、执行与服务商要求。
3.  首期可以提供外部钱包作为兼容性基线；若普通用户体验要求更高，再决定是否提供内嵌钱包。
4.  内嵌钱包必须评估密钥托管边界、账户恢复、用户退出、供应商迁移和安全责任。
5.  所有钱包路线都必须保留用户对资产和交易的明确控制与可理解的确认流程。

## 6. Gas 支付与跨链费用方案

### 6.1 四种支付模式

  -----------------------------------------------------------------------------------------------------------------------
  模式                      用户体验                   平台成本                             复杂度         建议
  ------------------------- -------------------------- ------------------------------------ -------------- --------------
  用户自行支付原生 Gas      用户需在源链准备原生代币   低                                   低             必须先实现

  平台赞助 Gas              用户可不直接准备原生 Gas   平台承担 Gas 与服务费                中高           作为可选体验

  用户用代币支付执行费      用户可用 USDC 等支付       有服务费、兑换/结算成本              中高           通过 PoC 验证

  跨链协议代付/覆盖目标链   减少用户在目标链准备原生   成本通常包含在路由费用或到账估算中   依协议而定     跨链重点验证
  Gas                       Gas 的需要                                                                     
  -----------------------------------------------------------------------------------------------------------------------

### 6.2 跨链成本必须拆分

一笔跨链交易的总成本至少应考虑：

-   源链交易 Gas；
-   源链 DEX 交易费；
-   桥接、流动性或跨链执行费；
-   目标链执行 Gas；
-   目标链 DEX 交易费；
-   Relayer、Bundler、Paymaster 或 Gas 抽象服务费；
-   聚合器或平台服务费；
-   价格影响、滑点与潜在汇率/兑换成本；
-   失败、重试或恢复流程可能产生的额外费用。

不能把供应商所说的"Gasless"直接等同于"无成本"。它通常表示 Gas
的支付方式被抽象或转移，而非网络资源不再产生费用。

### 6.3 三家执行供应商的公开费用线索

以下仅用于建立模型，不构成最终报价；上线前需在官方定价页、控制台和合同中复核。

-   **Gelato：** 官方 Gas Tank 文档说明，成本由链上 Gas
    和服务费构成；服务费可能是订阅费或按 Gas
    成本加价的模式。具体金额依所用产品而定。参考：https://docs.gelato.cloud/Paymaster-%26-Bundler/GasTank
-   **Etherspot：** 官网公开 Pay-As-You-Go 价格为每 250,000 credits 收费
    1 美元，主网 Gas 另按网络成本收取、不加价；不同 API endpoint 的
    credits
    消耗不同，且有最低充值要求。参考：https://etherspot.io/pricing/
-   **1Shot Public Relayer：** 官网公开规则为网络 Gas 低于 0.01
    美元时，每笔已确认交易总费用为 0.01 美元；Gas 高于 0.01
    美元时，按网络 Gas 成本加 20% 计费。该规则适用于其 Public
    Relayer，且需要满足其授权/账户执行模型。参考：https://1shotapi.com/pricing

### 6.4 平台赞助 Gas 的控制策略

如果最终决定补贴 Gas，建议设置：

-   每个用户的每日/每月赞助额度；
-   每笔交易最大可赞助金额；
-   只对指定链、资产和交易金额区间开放；
-   对新用户、异常地址和高频失败请求进行限流；
-   交易模拟和费用估算失败时拒绝赞助或退回用户自行支付；
-   监控单用户成本、成功率和异常增长；
-   对报价与签名之间的时间差设置费用上限与报价过期策略。

## 7. 费用与单位经济模型

### 7.1 单笔交易总成本

建议用以下模型统一比较不同路由和供应商：

``` text
单笔总成本 =
  源链 Gas
+ 源链 DEX 费用
+ 跨链协议/桥接费用
+ 目标链执行 Gas
+ 目标链 DEX 费用
+ Relayer/Bundler/Paymaster 服务费
+ 聚合器费用
+ 平台承担的补贴
+ 失败/重试/恢复的期望成本
```

为了避免重复计算，实际计算时应依据报价字段确认哪些费用已包含在预估到账量中、哪些费用另行扣除。不得把已经从到账金额中扣除的费用再加一次。

### 7.2 用户净到账与平台收益

对用户而言，应尽量比较：

``` text
用户净到账价值 = 目标资产预计到账量 × 目标资产参考价格
```

同时展示最低到账量和估算风险。不要只比较源链输入金额或"桥费"单项。

对平台而言：

``` text
平台单笔贡献毛利 =
  平台收取的交易服务费
- 平台承担的 Gas 补贴
- 平台承担的供应商服务费
- 与该笔交易直接相关的其他可变成本
```

如果某项供应商费用已包含在用户支付的路由费中，应明确成本承担方，避免在平台成本和用户费用里重复记账。

### 7.3 费用测试矩阵

至少覆盖以下维度：

  维度       测试样本建议
  ---------- ------------------------------------------------
  交易方向   同链 Swap、跨链兑换
  金额       小额、中额、大额三档
  资产       主流稳定币、原生资产、高流动性代币
  路由       主供应商、对照供应商、可用的直接协议路径
  Gas 模式   用户付 Gas、平台赞助、代币支付（如可用）
  状态       成功、报价过期、源链失败、目标链延迟、部分完成
  时间       不同时间段重复采样，避免只看单一时点

每笔记录至少包含：时间、链、资产、金额、供应商、报价耗时、预计到账、最低到账、费用分项、源链
Gas、目标链费用、实际到账、完成时间、最终状态和失败原因。

## 8. 跨链状态机与异常恢复

### 8.1 推荐的内部状态

``` text
CREATED
  ↓
QUOTED
  ↓
AWAITING_USER_CONFIRMATION
  ↓
AWAITING_SOURCE_SIGNATURE
  ↓
SOURCE_SUBMITTED
  ↓
SOURCE_CONFIRMED
  ↓
BRIDGE_OR_CROSSCHAIN_PENDING
  ↓
DESTINATION_EXECUTING
  ↓
COMPLETED
```

异常状态应至少包括：

``` text
QUOTE_EXPIRED
USER_REJECTED
SOURCE_FAILED
CROSSCHAIN_DELAYED
DESTINATION_FAILED
PARTIALLY_COMPLETED
REFUND_PENDING
REFUNDED
MANUAL_REVIEW_REQUIRED
```

状态机应允许从延迟状态继续推进，不能把暂时未查询到目标链交易等同于失败。

### 8.2 异常处理原则

-   **报价过期：** 重新报价并要求用户确认关键变化。
-   **用户拒绝签名：** 结束本次用户操作，不视为链上失败。
-   **源链交易失败：** 展示失败原因；确认是否实际消耗了 Gas。
-   **源链成功但目标链延迟：**
    持续查询并展示预计状态，不要要求用户盲目重复提交。
-   **目标链执行失败：** 查询供应商/协议是否有恢复、退款或手动处理路径。
-   **部分完成：**
    明确说明资产当前在哪里、已完成哪些步骤、下一步是否需要用户操作。
-   **Webhook 重复投递：**
    处理逻辑必须幂等，避免重复创建事件或错误覆盖终态。
-   **供应商 API 不可用：**
    保留本地订单和链上交易哈希，支持后续恢复查询。

### 8.3 最低监控指标

-   报价成功率与无可用路由比例；
-   报价 P50/P95 响应时间；
-   源链提交成功率；
-   源链成功后最终完成率；
-   目标链完成时间 P50/P95；
-   部分完成与退款比例；
-   预计到账与实际到账偏差；
-   每笔交易总成本与平台补贴；
-   状态同步延迟、Webhook 失败率和重复事件率。

## 9. 安全与风险清单

  ----------------------------------------------------------------------------------------------------------
  风险                           影响                       首期控制措施
  ------------------------------ -------------------------- ------------------------------------------------
  恶意代币、假币或低流动性资产   资产损失、无法卖出         默认代币白名单、风险提示、流动性与价格影响检查

  无限授权或恶意 spender         资产被滥用                 显示 spender、优先最小授权、授权管理与撤销入口

  报价过期或滑点过大             实际到账低于预期           报价 TTL、最小到账量、滑点上限、重新确认

  恶意或异常 calldata            资产损失                   校验目标地址、方法、token、金额和
                                                            spender；模拟交易

  EIP-7702 委托风险              EOA                        审核委托代码、权限范围、撤销流程和钱包提示
                                 在委托期间执行非预期逻辑   

  Paymaster/赞助滥用             平台成本异常增长           额度、限流、白名单、交易模拟与异常检测

  跨链延迟或部分完成             用户误以为交易丢失         独立状态机、链上对账、恢复指引和人工处理通道

  供应商中断或限流               报价/状态不可用            适配层、健康监控、备用查询路径和供应商退出预案

  状态同步错误                   错误显示成功/失败          用链上回执和供应商状态交叉校验，保留审计日志
  ----------------------------------------------------------------------------------------------------------

**原则：**
任何"交易已完成"的用户提示都应有可验证的目标链结果作为依据。安全审计、法律合规和商业条款应在上线前由相应专业人员复核。
