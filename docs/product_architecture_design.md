# 多链 DEX 交易执行平台 · 产品架构设计

- **文档版本：** v0.1
- **编写日期：** 2026-10-16
- **关联文档：** `okx_dex_api_development_testing_reference.md`（OKX DEX API 接入与测试参考）
- **文档定位：** 交易执行侧的架构设计；不含资金来源、策略与交易指令的生成逻辑

## 1. 定位与边界

**产品做什么：**

- 接收上游交易指令，在多链 DEX 上完成自动执行与结算；
- 维护一个自持密钥的多链资金账户，用作执行账户；
- 负责报价、路由、签名、广播、状态跟踪、记账与审计。

**产品不做什么：**

- 不解决资金来源与托管问题（只做交易执行）；
- 不生成交易指令（指令从何而来由上游系统决定）；
- 不设人工逐笔审批（指令到达即自动执行，风控以策略配置形式生效）。

## 2. 关键前提（已核实）

这些前提直接决定架构形状，均来自对 OKX 官方 DEX SDK 源码的核实：

| 前提 | 含义 |
|---|---|
| OKX 是非托管服务 | 不持有资金、不保管私钥、不代付 Gas、不代签名 |
| 广播接口入参是 `signedTx` | 签名必须由产品侧完成，OKX 只负责传播 |
| OKX 返回未签名 calldata | 选路与算价由 OKX 完成，签名与广播由产品完成 |
| EVM 各链共用一个地址 | 一个 EVM 密钥覆盖所有 EVM 链，余额与 Gas 逐链独立 |
| 非 EVM 地址不同 | Solana / Sui / TON / TRON 需要独立密钥对 |
| OKX 用 `chainIndex` 标识链 | 跨链接口同时需要 `chainIndex` 与 `chainId` |

> 结论：**产品自身就是那个钱包。** 密钥管理、nonce、Gas、广播、对账都是产品的核心职责，而非周边功能。

## 4. 模块清单

| # | 模块 | 核心职责 |
|---|---|---|
| M1 | 指令处理 | 接收指令、schema 校验、幂等键生成、去重、按账户串行化 |
| M2 | 风控门控 | 事前/事中/事后三层校验，输出放行或拒绝结论 |
| M3 | 报价与路由 | 报价获取、有效期管理、缓存、多源比价（OKX 为主，可扩展） |
| M4 | 执行与结算 | 授权检查、交易构造、字段校验、签名、广播、回执确认 |
| M5 | 账户与密钥 | 多链密钥集合、签名服务、nonce 管理、Gas 预算与补给 |
| M6 | 订单状态机 | 订单生命周期与状态迁移、超时判定、恢复判定 |
| M7 | 持仓与余额 | 链上余额、持仓快照、与内部账本对账 |
| M8 | 账本与成本 | 成交流水、费用（服务费/Gas/滑点/桥费）、盈亏归因 |
| M9 | 供应商适配 | OKX 端点与版本集中管理、错误映射、限流与降级 |
| M10 | 观测与审计 | 指标、告警、脱敏审计日志、链路追踪 |

## 5. 与原始四模块的对照

| 原始模块 | 处理方式 |
|---|---|
| a 交易模块 | 拆为 **M3 报价与路由** 与 **M4 执行与结算**（生命周期不同：报价只读可缓存，执行需门控与签名） |
| b 订单状态与仓位监控 | 拆为 **M6 订单状态机** 与 **M7 持仓与余额对账**（数据源与一致性问题不同） |
| c 交易指令处理 | 保留为 **M1**，并补齐幂等键、去重与按账户串行化 |
| d 风险监控 | 保留为 **M2**，但分事前/事中/事后三层（见第 10 节） |
| — | **新增 M5**（密钥/签名/nonce/Gas，最关键的缺口）、**M8**、**M9**、**M10**、**M11** |

## 6. 资金账户与密钥模型

- **EVM 侧：** 一个密钥、一个地址、覆盖所有 EVM 链；但**余额与 Gas 逐链独立**。
- **非 EVM 侧：** Solana / Sui / TON / TRON 各需独立密钥与地址。
- **整体模型：** 产品维护一个「多链密钥集合」而非单一账户；账本、限额、Gas 都按「链 × 资产」维度记账。
- **密钥存放：** 私钥只存在可信后端（KMS / HSM / MPC），不进日志、不进镜像、不进仓库；开发与生产使用不同密钥与不同 OKX API Key。
- **注意区分两种签名：** OKX API 请求签名（HMAC，用 Secret Key）与链上交易签名（用钱包私钥）是两套完全不同的机制，不要混在一个组件里。

## 7. 交易执行主流程

```text
指令到达
  → schema 校验 & 幂等键计算
  → 重复指令？是则直接返回既有订单
  → 事前风控（白名单/限额/滑点/余额/Gas）
  → 通过？否 → 拒绝并记录
  → 获取报价 & 校验有效期
  → allowance 检查 → 必要时先执行 approve（单独一笔交易）
  → 构造交易 & 字段校验（chainId / to / value / data / 金额）
  → 本地签名（nonce 由 M5 分配）
  → 广播（自建 RPC 或 OKX broadcast-transaction）
  → 跟踪回执 → 更新订单状态 → 记账 → 对账
```

**关键约束：**

- 报价过期必须重新报价，不允许用过期报价签名；
- 广播超时后**先查询**（`orderId` / `txHash` / nonce），确认原交易状态前不得重复提交；
- approve 是独立交易，需要自己的 nonce、Gas 与状态跟踪。

## 8. 订单状态机

```text
主路径：
  待接收 → 已校验 → 已放行 → 报价中 → 已报价 → [待授权] → 待签名 → 已签名 → 已广播 → 源链确认中 → 源链成功 → 完成

分支与终态：
  已放行   --风控拒绝--------> 已拒绝（终态）
  报价中   --无路由/已过期----> 已过期（终态）
  待签名   --签名失败---------> 失败（可重试）
  已广播   --链上回滚---------> 链上失败（终态）
  已广播   --超时未确认-------> 超时待确认 → 查询链上 → 恢复中 →（推进 / 已取消）
  源链成功 --跨链--------> 目标链处理中 → 完成
```

注：`[待授权]` 为可选步骤，仅在 ERC-20 且 allowance 不足时出现（原生币兑换无需授权）。

- **终态：** 完成、链上失败、已拒绝、已取消、已过期。
- **跨链不变式：** 源链成功不是终态；只有满足目标链完成条件才可标记完成。
- **「部分成交」语义：** 单链 Swap 通常是全成或全败；部分成交主要来自拆单路由或跨链，必须在状态机中显式定义。
- **持久化：** 状态机必须落库；服务重启后以链上数据 + `post-transaction/orders` 为准做一次对账再决定续跑。

## 9. 幂等、并发与崩溃恢复

- **幂等键：** 由指令参数派生（如 `hash(chainIndex + tokenIn + tokenOut + amount + 上游指令ID)`），同一幂等键只允许存在一个订单。
- **去重窗口：** 保留近期幂等键，拒绝重复指令而不是重复执行。
- **串行化：** 同一账户、同一条链上的交易必须串行或经 nonce 池调度，避免 nonce 冲突与覆盖。
- **nonce 管理：** 采用本地分配 + 链上确认校正的模型，处理 stuck nonce（同 nonce 提 Gas 替换）。
- **崩溃恢复：** 启动时对「非终态订单」逐笔回查链上状态，再决定推进、重试或标记失败。

## 10. 风控设计（三层）

**事前（放行前，返回通过/拒绝）**

- 白名单：链、代币、交易目标地址（`to`）、spender（OKX DEX router）；
- 限额：单笔上限、单链敞口上限、单日累计上限、Gas 预算；
- 报价质量：滑点上限、价格相对参考价的偏离度、报价有效期；
- 资金条件：源链余额充足、Gas 充足、allowance 状态已知；
- 指令合法性：金额为正、精度合法（最小单位整数或字符串，禁用浮点）。

**事中（执行中）**

- 广播失败/超时、同 nonce 竞争、卡单；
- 实际滑点超过阈值、成交价异常；
- 重复订单检测（同一幂等键并发到达）；
- 熔断：连续失败、异常拒绝率、供应商错误率超阈值时触发停止开关。

**事后（完成/失败后）**

- 内部账本与链上余额对账，差异告警；
- 异常亏损、在途资金（in-flight）超限告警；
- 授权残留检查，回收不必要的 allowance。

> 自动执行模式下，「人工批准」不再是一个流程节点，而是**风控配置 + 停止开关**：所有闸门以策略形式写在 M2/M11 中，可在线调整、可一键停机。

## 11. 供应商适配与降级

- **端点集中管理：** 聚合器 `/api/v6/dex/aggregator/*`、交易上链与跨链 `/api/v5/dex/*`，版本分散在配置中维护，不散落在业务代码。
- **统一错误模型：** 把 OKX 业务码映射为内部 `ProviderError`（可重试性、用户语义、指标标签）。
- **限流与配额：** 按额度做请求调度，报价做短期缓存，避免无谓消耗配额。
- **降级策略：** 供应商故障时优先「暂停执行」而非「改用未验证路径」；跨链可指定 `allowBridge`/`denyBridge` 限定可信桥。
- **广播通道可切换：** 自建 RPC 与 OKX 广播服务互为备份。

### 监控能力边界（重要）

OKX 只提供**订单级状态回查**，不提供链上执行监控服务。可直接复用的只有两个轮询接口：

| 接口 | 覆盖范围 | 限制 |
|---|---|---|
| `GET /api/v6/dex/aggregator/history` | 按 `txHash` 查单链兑换最终状态（`pending`/`success`/`fail`），含区块高度、交易类型、from/to | 仅能查"经 OKX DEX API 发出"的交易 |
| `GET /api/v5/dex/post-transaction/orders` | 广播订单列表（排队中/成功/失败 + `failReason`），游标分页，最多 100 条 | 仅覆盖"通过 OKX 广播接口发出"的订单 |

**必须自建的部分：**

- 跨链目标链监控：OKX 无任何跨链状态接口，目标链到账需自行对接桥方或目标链节点；
- 确认数、最终性与 reorg 处理；
- 卡单/pending 交易的替换与 nonce 管理；
- 余额与持仓监控（需自行查 RPC）；
- 事件推送（OKX 只有轮询，无订阅），以及轮询退避与配额控制。

**由此得出的两个设计约束：**

1. 广播通道的选择会决定监控能力：走 OKX 广播才有 `orders` 接口（含失败原因）；走自建 RPC 则完全靠自己查回执。建议把广播通道作为可配置项，并在订单上记录实际使用的通道。
2. M6 与 M7 必须以链上数据（自建 RPC + 归集区块）为事实来源，把 OKX 的状态接口当作**辅助交叉校验**，而不是唯一真相来源。

## 12. 领域数据模型

| 对象 | 关键字段（示意） |
|---|---|
| `Chain` | `chainIndex`、`chainId`、原生币、确认数要求、Gas 模型 |
| `Token` | 地址、精度、符号、所在链 |
| `Account` | 密钥/地址、所属链族、启用状态 |
| `Quote` | 输入/输出代币与金额、最低输出、路由、费用、有效期 |
| `Approval` | 代币、spender、额度、状态、交易哈希 |
| `Order` | 幂等键、状态、报价快照、交易哈希、`orderId`、重试次数 |
| `Leg` | 订单的子交易（如源链/目标链两段），各自哈希与状态 |
| `LedgerEntry` | 订单/腿、资产、金额、方向、费用类型、时间 |
| `RiskLimit` | 维度（链/代币/账户）、限额值、生效窗口 |
| `AuditEvent` | 操作者、动作、前后快照、时间、脱敏后的敏感字段 |

> 字段最终以实际 API 响应为准，不要假设不同链、不同接口的响应结构一致。

## 13. 可观测性与审计

- **指标：** 指令吞吐、放行/拒绝率、报价成功率与延迟、签名耗时、广播成功率、确认耗时、gas 实际/预估比、对账差异数、在途资金。
- **告警：** 连续失败、对账不平、在途超限、报价过期激增、供应商错误率、nonce 卡住。
- **审计：** 每笔交易记录报价快照、签名前交易摘要、实际成本与结果；日志对 API Key、签名、私钥、Passphrase 一律脱敏。
- **追踪：** 以订单 ID 贯穿指令 → 报价 → 签名 → 广播 → 确认 → 记账全链路。

## 14. 安全与非功能要求

- 私钥与 OKX Secret Key 分离存放，最小权限访问；
- 开发/生产环境隔离（不同密钥、不同 API Key、不同额度）；
- 主机时钟需与标准时间同步（OKX 要求请求时间偏差不超过 30 秒）；
- 金额全部使用最小单位整数或字符串；
- 关键操作（限额调整、开关切换）留痕并可回放。

## 16. 待决问题

1. **指令契约：** 上游指令的最小字段集合与传输方式（同步 API / 消息队列）尚未定义，需要与上游系统对齐。
2. **支持的链范围：** 首期支持的 EVM 链清单与非 EVM 链是否纳入本期。
3. **自动化程度：** 全自动的同时是否需要保留「大额指令二次确认」这类例外闸门。
4. **多账户需求：** 是否需要按策略/租户隔离账户，以便盈亏归因。
5. **跨链范围：** 首期是否纳入跨链，还是先做单链再加跨链。
